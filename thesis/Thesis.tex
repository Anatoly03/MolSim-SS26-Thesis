\vspace*{2cm}
\begin{center}
    {\Large \bf Abstract}
\end{center}
\vspace{1cm}

In the past decades, Rust has gained more admiration as a low-level, performant and memory-safe programming language, while C++ remains the dominant choice for high-performance computing in the academic field. This thesis presents empirical results by implementing three distinct algorithmic molecular dynamics approaches in both Rust and C++.

Both languages implement three different approaches in particle management and computation patterns, with DirectSum computing over all particle pairs in the hot loop, LinkedCells introducing a three-dimensional chunk system to reduce the overall workload, and DirectSumParallel using multi-threaded paradigms to accelerate computation.

This thesis aims to inform the decision of whether to adopt Rust in emerging software for performance-critical applications with high memory-safety requirements, showing that Rust can slightly outperform C++ in competitive environments.

\section{The Rust Ecosystem}

Before diving into the syntax and the defining elements of the Rust Programming Language, this section will give a brief overview over the tooling and console applications provided by Cargo, the Rust Package Manager.

Since Cargo can install dependencies it was also designed to be extensible, meaning that most operations you will need to maintain a Rust project are located behind a Cargo subcommand.

\begin{description}
    \item[cargo run] Shortcut for Cargo to invoke the Rust compiler on the codebase and then execute the resulting binary.
    \item[cargo build] Equivalent to \texttt{make}, Cargo will invoke the Rust compiler on the codebase and compile a binary but not execute it.
    \item[cargo test] Equivalent to \texttt{ctest} or GoogleTest, Cargo has an integrated testing tool which will compile the codebase and run all functions annotated with \texttt{\#[test]} as an individual, isolated test case.
    \item[cargo doc] Equivalent to \texttt{Doxygen} or other documentation libraries, Cargo provides a built-in way of generating documentation for the codebase.
    \item[cargo fmt] Equivalent to \texttt{clang-format}, Cargo provides a built-in way to format the entire codebase.
    \item[cargo clippy] Equivalent to \texttt{clang-tidy}, Cargo provides a built-in way to lint and statically analyze the codebase. This command is also often used in CI/CD to ensure the codebase quality.
\end{description}

The first observation in terms of differences in usability is that the C++ infrastructure is fragmented, whereas for Rust it is centralized via its package manager. This smoothes down the learning curve of Rust tools, as new users only have to get comfortable with Cargo, which provides access to dependency management, compilation, linting, and further community-written subcommands.

It is noteworthy to mention that there is no equivalent to GDB as a memory safety analyzer in the Rust ecosystem because the type system and ownership model of Rust guarantees safety over memory and thread.

\subsection{Structs and Traits}

Structs in Rust are almost entirely equivalent to C++ structs. A struct is a type which defines a collection of fields. However, unlike in C++, Rust has no concept of struct inheritance. Instead of abstract classes, Rust provides traits~\cite{rust-book-traits} as seen in~\autoref{code:rust-trait}: An abstract interface that types can implement explicitly. This introduces the concept of ``composability'' in Rust, giving one type the ability to express multiple traits.

\vspace{0.5em}
% \setlength{\columnsep}{2em}
% \begin{multicols}{2}
% \begin{lstlisting}[style=eclipse-cpp, caption=An abstract class in C++, label=code:cpp-abstract-class]
% class Force {
%     virtual double potential(const Particle &particle, const Particle &other) const;
% }
% \end{lstlisting}

% \vfill\null
% \columnbreak

\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption={A Trait definition in Rust (Do not be confused that there is no \texttt{return} keyword: The last line is considered the return value if it is not followed by a semicolon)}, label=code:rust-trait]
pub trait Force {
    fn potential(&self, particle: &Particle, other: &Particle)
        -> f64;

    fn force(&self, particle: &Particle, other: &Particle) -> Vec3 {
        let potential = self.potential(particle, other);
        let diff = Particle::position_difference(other, particle);
        -diff * (potential / diff.length2())
    }
}
\end{lstlisting}

A trait is, more comparable to the concept in Java, an abstract interface, defining the interface name and a collection of methods. Some methods can have a default definition and thus do not need to be redefined. Traits are explicitly implemented for types with an implementation block as seen in~\autoref{code:rust-trait-implement}.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption=An implementation of the Force trait in Rust (Note: A comparison whether distance is zero is omitted for code flow simplicity), label=code:rust-trait-implement]
impl Force for NewtonForce {
    fn potential(&self, particle: &Particle, other: &Particle)
    -> f64 {
        let distance = Particle::distance(particle, other);
        let mass_prod = Particle::mass_product(particle, other);
        -self.factor * mass_prod / distance
    }
}
\end{lstlisting}
% \end{multicols}

Similar to C++  operator overloads, Rust allows to overload some operators using trait implementations, providing similar syntactic sugar to overload operators like in C++.

For example, the infix notation of the $+$ operator can be defined with the trait \texttt{Add<Rhs>}, where the self type acts as left-hand side and the generic type \texttt{Rhs} defines the type of the right-hand side. This way, string buffers can be concatenated over the same operator as integers are being summed over. In~\autoref{code:rust-trait}, we use the overloaded operator $*$ to allow multiplication of the custom vector type implementation with a scalar. Since implementing such a trait involves some more complex Rust concepts, its explanation is moved to the appendix in~\ref{section:rust-implement-add-appendix}.

This `atomicity' of an implementation block is good from the perspective of codebase maintenance and developer experience for two reasons: Firstly, it allows for code readability, differentiating between ``type methods'' and ``trait implementation''. Secondly, by enforcing an implementation into a distinct scope, this prevents a collision between traits using the same identifier for a method.

As the second argument can cause some confusion with how Rust resolves the ambiguity with overlapping trait method names, appendix note~\ref{section:rust-trait-same-identifier} offers some clarification. However, this is mostly irrelevant to the thesis and skipped here.

\subsection{Ownership Model}

One of the most distinctive features of Rust is the ownership model, which enables zero-cost memory safety by hinting the compiler where an element is ``alive'' and when it needs to be ``removed''. This is fundamentally different to the approach in C where the developer is directly involved in memory allocation and freeing.

C++ resolves this, unlike pure C, with lifetimes and destructors but these are a runtime-feature\cite{cpp-lifetimes} and the compiler does not enforce lifetimes leaking out of scope, leading to undefined behaviour. In both C and C++ the developer is directly responsible for memory safety.

According to the Rust Programming Language book, a value in Rust must follow three rules: (R1) The value has an owner, (R2) and only one owner at any time. (R3) When the owner leaves the scope, without passing on ownership, the value will be dropped~\cite{rust-book-ownership-rules}. This way, ownership of a value can be moved into a function call, and ownership of a value can be returned from a function.

The second rule makes it difficult to read a value multiple times without consuming it. This is where references get introduced, which is also referred to as ``borrowing''. This concept follows two additional rules: (R4) At any given time, an item can either have one mutable reference or multiple immutable references, (R5) and any reference must be valid~\cite{rust-book-borrowing}.

Before evolving an intuition to these rules consider the following examples:

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption=Code breaks Rule 5, label=code:rust-err1]
let a = String::from("Hello, World!");
{
    let b = a;      // a is moved here as 'b'
}                   // b is destroyed here
println!("{}", &a); // error: invalid reference (R5)
\end{lstlisting}

In~\autoref{code:rust-err1} we encounter a compilation problem: As the variable \texttt{a} gets moved into an inner scope by being assigned to \texttt{b}, it gets destroyed at the end of the inner scope (R3). This means that when we try to print the string contents of \texttt{a}, we disobey Rule 5: The reference is invalid.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption=Code breaks Rule 4, label=code:rust-err2]
let a = String::from("Hello, World!");
let b = &mut a;     // we borrow 'a' mutably to 'b'
println!("{}", &a); // error: invalid borrow (R4)
\end{lstlisting}

In~\autoref{code:rust-err2} we encounter a similar problem, but this time the reasoning is a bit different. Since we borrow \texttt{a} mutably to \texttt{b}, we are prevented from creating immutable borrows of \texttt{a} due to Rule 4: Either one mutable borrow or multiple immutable borrows. This prevents a lot of actions automatically: Reading \texttt{a} requires immutable borrow, which breaks Rule 4, and modifying \texttt{a} requires a mutable borrow, which breaks the same rule.

Intuitively, when a value is borrowed mutably, the owner is prevented from exercising most actions on it: Only the borrower can read and write the value during the borrow.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption=Code breaks Rule 1 and 5, label=code:rust-err3]
fn return_hello() -> &String {
    let a = String::from("Hello, World!");
    return &a; // borrow of 'a' is returned
               // 'a' is dropped here -> &a is invalid here
}
\end{lstlisting}

In~\autoref{code:rust-err3} we encounter what is generally called a ``dangling reference''. Since the local variable \texttt{a} is removed at the end of the function, returning a reference to this local variable would cause undefined behaviour. The equivalent C++ code would be the following:

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-cpp, basicstyle=\ttfamily\small, caption=C++ code breaks Rule 1 and 5 but compiles with a warning, label=code:cpp-err3]
#include <string>

std::string* return_hello() {
    std::string a = "Hello, World!";
    return &a; // reference of 'a' is returned
               // 'a' is dropped here -> &a is invalid here
}
\end{lstlisting}

The erroneous Rust code example in~\autoref{code:cpp-err3} would compile in C++ which means that by enforcing the ownership and reference rules, Rust eliminates an entire class of bugs, which would cause mutation side effects and undefined behaviour in C and C++.

\subsection{Dynamic Dispatch}

Both the C++ and Rust implementations use dynamic dispatch to up-cast a type into an abstract interface at runtime. This is not a zero-cost abstraction, but allows for a fair comparison and code writing simplicity.

For example, the types \texttt{NewtonForce} and \texttt{LennardJonesForce} both implement (or inherit, for the C++ codebase) the \texttt{Force} trait. For the simulation run, we convert both force implementations into a dynamic \texttt{Force} object. At the cost of losing all information on the underlying type, we get a black box of a model, capable of yielding the potential and force interaction for any two particles. The equivalent in C++ is achieved through inheritance and virtual functions.

The in-language implementation of both paradigms is also a bit different: In C++ an object of a polymorphic type comes with ``vtable pointers'', a table of every virtual method and the mapping to the correct implementation, which is resolved at runtime. In Rust, a reference can be coerced into a smart pointer with the \texttt{dyn} keyword as seen in~\autoref{code:rust-dyn}.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption=Dynamic Coercion in Rust, label=code:rust-dyn]
let newton = NewtonForce { factor: 5.0 };
let force: &dyn Force = &newton;

println!("Potential: {}", force.potential(...))
\end{lstlisting}

\autoref{code:rust-dyn} shows a minimal example of how such a cast looks like syntactically.

\subsection{Enums}

Rust enums are a special branched type, which are a superset of C++ enums in terms of usage, as it is follows the more functional concepts like in OCaml. Consider the following enum implementation in~\autoref{code:rust-option}.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption=Optionality in Rust, label=code:rust-option]
pub enum Option<T> {
    Some(T),
    None
}
\end{lstlisting}

This type defines an optionality over a generic type, which can be either set (\texttt{Some}) or unset (\texttt{None}). In Rust, every enum member is more akin to an individual struct, being able to define custom attributes. You can define the enum member \texttt{Some(T)} as \verb|Some{value: T}|.

The power of enums in codeflow then comes from the pattern matching keyword \texttt{match}, which allows to run code conditionally based on the enum branch as seen in~\autoref{code:rust-option-method}.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption={Optionality in Rust}, label=code:rust-option-method]
impl<T> Option<T> {
    pub fn is_some(&self) -> bool {
        match self {
            Some(_) => true,
            None => false,
        }
    }
}
\end{lstlisting}

We will now deconstruct the above example to understand the Rust programming language better: The first line \texttt{impl<T> Option<T>} defines an implementation block with the generic \texttt{T} for an option with the specified generic. This means that all constants and functions in this scope are member of \texttt{Option}.

The second line defines the method \texttt{Option<T>::is\_some}, which is non-static, since it has the special argument \texttt{\&self} -- from earlier sections we also know that this method borrows the value immutably.

The third line defines the \texttt{match} block and also the return value of the function: If the value is matched \texttt{Some}, return \texttt{true}, otherwise \texttt{false}.

Since enums are powerful in control flow, they also become the basis of Rusts' error handling. Consider the following simplified implementation of a result type:

Rust provides another way to raise errors, which is called \texttt{panic}. While a \texttt{Result} is for recoverable errors, panic is for unrecoverable program states, in which the stack is unwinded and only the destructors are invoked. This is comparable to a \texttt{throw} without a \texttt{catch}.

\subsection{Unsafe Rust}

What we have learned so far has been `Safe Rust', which can be statically analyzed for memory safety, and bugs that would cause segmentation fault in C++ are caught in the compilation stage.

However, occasionally, because of performance optimizations using pointer arithmetics or linking external binaries, code has to be written in a way which the compiler can not statically analyze. This mode is commonly referred to as `Unsafe Rust'.

An unsafe functionality is a scope, function or trait implementation annotated with the \texttt{unsafe} keyword. In an unsafe block, Rust gives you access to a few operations which can not be statically verified and could cause undefined behaviour. The operations are the following.

\begin{enumerate}
    \item Dereferencing a pointer.
    \item Using other unsafe functionalities, like invoking an unsafe function or implementing an unsafe trait.
    \item Read or write to a mutable static variable.
    \item Accessing fields of a \texttt{union}, a special element which is syntactically similar to a struct with the exception of all fields sharing the same storage.
\end{enumerate}

To get a bit of intuition on what kind of operations are unsafe consider this example: For a struct to be shared across threads, it needs to implement the \texttt{Sync} trait, which is unsafe. If the struct also contains a pointer which you would like to interpret at index $2$, adding $2$ to the pointer and dereferencing it is also unsafe behaviour.

\chapter{Application with Molecular Dynamics}

In this chapter, we will explain the molecular dynamics algorithms from a mathematical and theoretical perspective, and the next chapter will dive into a more detailed technical explanation of the implementation.

Most of the physics equations and concepts presented in this section are based on the book ``Numerical Simulation in Molecular Dynamics'' by Michael Griebel~\cite{numerical-simulation}.

\section{Overview of the Physics System}

We are given the three-dimensional simulation state ${\mathcal S} = (\mathcal P, t_c, t_e, \delta, U)$ where $\mathcal P$ is a set of particles $p_i \in \mathcal P$, $t_c \in \mathbb R$ is the current time, $t_e \in \mathbb R$ is the total (or ``end'') time, $\delta \in \mathbb R$ the delta time per simulation step and $U$ the potential evaluation function $(p_i, p_j) \mapsto \mathbb R$. The total time $t_e$ specifies the overall physical duration of the simulation and $\delta$ the precision of the simulation. 

Furthermore, a particle $p_i$ is the tuple $p_i = (x_i, v_i, f_i, m_i)$ with $x_i \in {\mathbb R}^3$ representing the position of the particle, $v_i \in {\mathbb R}^3$  velocity, $f_i \in {\mathbb R}^3$ its force,
% $o_i \in {\mathbb R}^3$ its force in the previous time step (old force) 
and $m_i \in \mathbb R$ its mass. We also declare the notation $p_i^k$ as the particle $p_i$ at time step $k$ and ${\mathcal S}^k$ as the simulation configuration at time step $k$.

The goal of the physics system is to create a function ``\texttt{tick}'' which applies physically correct behaviour every simulation step for an initial configuration ${\mathcal S}^0$ as seen below in Equation 3.1.

\begin{align}
{\mathcal S}^{k + 1} := \texttt{tick}\left( {\mathcal S}^k \right)
& \forall k \in {\mathbb N}^+
\end{align}

To achieve this, we build \texttt{tick} as a pipeline of different functions which update the position, then the force and then the velocity (in this order).

\section{Updating Position and Velocity}

The simulation is on paper a continuous problem which gives the exact location of every particle for a given time step. Due to the limitations of digital computers we rely on time discretization~\cite{numerical-simulation} for our physical equations. The position and force update functions are derived below in Equations 3.2 and 3.3.

% self.position += self.velocity * delta_time + self.force * (delta_time.powi(2) / (2.0 * self.mass));
\begin{align}
x_i^{t+1} := v_i^t \delta + f_i^t \frac{{\delta}^2}{2m_i}
\label{pipeline-update-position}
\end{align}

% self.velocity += (self.force + self.old_force) * (delta_time / (2.0 * self.mass));
\begin{align}
v_{t+1} := \left(f_i^t + f_i^{t-1}\right) \cdot \left(\frac{\delta}{2m_i}\right)
\label{pipeline-update-velocity}
\end{align}

Note that in Equation 3.3 we rely on the force from a previous time step. Algorithmically this is achieved by storing the delayed force (or ``old force'') in the particle tuple.

\section{Force Interface}

As previously mentioned, the potential function $U$ is stored in the simulation state $\mathcal S$. This is mostly due to a requirement from a legacy project where the force type could be dynamically set. We provide the following two potential functions, the Newton potential $U_\text{N}$ in Equation 3.4 and the Lennard-Jones potential $U_\text{LJ}$ in Equation 3.5.

\begin{align}
U_\text{N} := - G \cdot \frac{M}{r}
\label{potential-newton}
\end{align}

The Newton potential uses the gravitational constant $G = 1$, the particle mass product $M = m_i \cdot m_j$ and the scalar distance $r = |p_i - p_j|$ between the two particles $p_i$ and $p_j$. The force is proportional to the product of the particle masses and inversely proportional to the distance.

\begin{align}
U_\text{LJ} := 4 \cdot \epsilon \cdot \left[{{\left(\frac{\sigma}{r}\right)}^{12}} - {{\left(\frac{\sigma}{r}\right)}^6}\right]
\label{potential-lennard-jones}
\end{align}

The Lennard-Jones potential relies on the particle distance $r$ and the constants $\epsilon = 5$ and $\sigma = 1$ which define the particle material. % We will not get to an intuitive understanding of what these constants represent.
Additionally we introduce a cut-off radius $r_c = 3$, which sets the potential to zero for a particle pair with $r > r_c$, mostly for performance reasons.

The force on the particle pair is then computed using the equation $F_X = -\frac{U_X}{r}$ where $r$ is the scalar distance, and the direction is along the vector connecting both particles, or intuitively: The potential is equal to the resulting force vector length. The particle force $f_i$ is computed as the sum of all forces with every other particle.

\section{Linked Cells}

The problem with the naive pairwise computation approach, which we refer to as DirectSum, is the performance bottleneck: Since we iterate over particle pairs, the performance of the algorithms is in $\mathcal O (n^2)$ (we say the performance is in ``n-square''). This means that if the particle count is doubled, the computational runtime grows by a factor of at least 4.

We attempt another algorithm, which we call LinkedCells. The idea is that we strategically divide the simulation space into cells (or ``chunks'') and reduce the overall particle pairs needed to compute. This depends on the assumption, that the potential is approaching zero for growing particle distances, in other words if particles further away exercise near-zero force.

The algorithm declares for simplicity, that every cell is its own simulation state ${\mathcal S}_i$, or intuitively an independent sub-system. This means that updating position and velocity is as simple as iterating over every cell and invoking the respective pipeline function, or a two-layer recursion. After position is updated, as an addition to DirectSum, we have to make sure that particles moving between cells is accounted for. In-code this process is called ``reindexation'': Every particle's position is tested for cell bounds, and out of bounds particles are inserted into other, regional cells.

The pairwise iteration needs to consider two scenarios, and the resulting force update function is a sequential combination of both:

\begin{enumerate}
    \item \textbf{Particles within a cell.} For particle interactions within a cell, we simply invoke the pairwise iteration recursively. We can do this since it is assumed that every cell is its own simulation state.
    \item \textbf{Particles across cells.} The more tricky part is to compute particle pairs which are located in different cells.
    
    In our approach, we first iterate over pairs of neighbouring cells. This is relatively easy as cells are stored at static positions and we can test if two cells are neighbours by checking if the difference on every axis is less than one chunk size.

    This becomes complete when for every cell pair, all particles of one cell are paired with particles in the other cell.
\end{enumerate}

This algorithm ensures that the force is only updated for particle pairs in close proximity, which eliminates most of the computation.

\section{Newtons' Third Law}

If $F_{i \rightarrow j}$ is the force which the particle $p_i$ exercises on $p_j$, then $p_j$ also exercises the inversion of the force on $p_j$ as seen in Equation 3.6.

\begin{align}
F_{i \rightarrow j} = - F_{j \rightarrow i}
\label{newton-three}
\end{align}

This fact is used to optimize the naive approach (DirectSum), by halving the amount of particle pairs needed to iterate over.

\section{Molecular Dynamics Simulation}

The molecular dynamics codebase is organised into three primary modules (in Rust they are called ``crates''): The program frame (binary entry point), the core library, and the I/O library. This modularity allows the core simulation methods to be tested.

From a high-level perspective, the code runs as follows: The frame module reads the program arguments from the console and invokes the I/O module on the input argument to read the initial particle state. This file also defines which force system and algorithmic implementation to use.

The frame program then defines the simulations' ``hot loop'' (also called iterations, ticks, internally referred to as steps) and writes the output configuration frequently. When the current time reaches the end time $t_c \geq t_e$, the simulation halts.

\subsection{Program Frame}

The program frame serves the entry point for the command line invocation and parses the console arguments, invoking the I/O library, setting up the simulation and then running the simulation loop the rest of the program lifetime.

\subsection{I/O Library}

The I/O library relies on the dependency Serde for general serialization and deserialization. Serde is the standard of serialization and deserialization across the Rust package ecosystem, having reached over 1 billion all-time downloads~\cite{rust-crates-serde}.

It provides the traits \texttt{Serialize} and \texttt{Deserialize} that map Rust types into and from an internal data format. Various data formats like JSON, YAML or VTU can then implement the traits \texttt{Serializer} and \texttt{Deserializer} to communicate with Serde's internal data format. The derive macros \texttt{\#[derive(Serialize, Deserialize)]} can be used to automatically generate the proper mapping. In the project, this is extremely helpful for the structs \texttt{FileDefinition} and \texttt{Particle}. This way, most of the input validation is once again moved to a dependency and there is no need implement checks for missing fields yourself.

\subsubsection{Writing Output}

For writing data we could in theory use the same approach in reverse, with \texttt{to\_string} methods and file writing, however due to a requirement from a legacy project, we needed custom comments in the written output, as well as more sophisticated control around file writing. That's why we implemented a \texttt{Writer} trait and a static method which selects the appropriate file writer.

The writer selection is done through the \texttt{--output} variable in the console line arguments. The extension of the input is parsed, and a similar approach like in~\autoref{code:rust-try-from-serde} is used to select the correct writer. \subsection{Core Library}

The core library exposes a lot of reused items, like the particle struct, the custom vector implementation, the particle container- and simulation traits and their implementing types.

\subsubsection{Core Structs}

The main types in the core library are the \texttt{Particle} struct as well as the custom vector type \texttt{Vec3<T>} over the generic scalar type \texttt{T}, which is statically set to the 64-bit float type.

The vector type overloads all mathematical operations to support addition with other vectors and multiplication with scalars, which is useful in the physics-applying functions in terms of code readability.

The particle struct exposes utility methods like measuring distance between two particles and applying the position and velocity update formulas.

\subsubsection{Forces}

There are two forces, \texttt{NewtonForce} and \texttt{LennardJonesForce} and both inherit the shared behaviour of a \texttt{Force}, which can compute the potential between two particles and the force. In Rust this is implemented by defining a trait \texttt{Force} and implementing this trait for the forces, while C++ uses struct inheritance with virtual functions. Both Rust and C++ use dynamic dispatch to achieve this abstraction in the simulation loop.

\subsubsection{Particle Container}

There are three implementations, \texttt{DirectSum}, \texttt{LinkedCells<C>} and \texttt{DirectSumParallel} and all inherit the shared behaviour of a \texttt{ParticleContainer}. In Rust and C++ the implementation follows the equivalent abstraction pattern like for forces.

The beauty of this implementation is, that the generic parameter \texttt{C} in the LinkedCells implementation is also required to implement behaviour of \texttt{ParticleContainer}. This means that in both Rust and C++ we can generate the types \texttt{LinkedCells<DirectSumParallel>} (``linked cells implementation with parallelization in every cell'') and \texttt{LinkedCells<\\LinkedCells<DirectSum>>} (``two-layer recursive linked cells, where the simulation cells are further divided into smaller cells'') which would define the behaviour of the cell, however these were not used in the final implementation.

\subsubsection{Simulation}

The simulation implements, in theory, the \texttt{ParticleContainer} trait. However, since Rust treats the same type with distinct generics as distinct types, a special \texttt{SimulationTrait} is created. The \texttt{FileDefinition} from the I/O library then defines a conversion into a dynamic simulation. 

\subsection{Direct Sum}

The first algorithmic approach is the \texttt{DirectSum} implementation which uses an iteration over all particle pairs and serves as the base of other implementations, which attempt to accelerate this naive approach. The pairwise iterations can be seen below in Listings~\ref{code:rust-directsum-foreach-pairs} (Rust) and~\ref{code:cpp-directsum-foreach-pairs} (C++).

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption={The particle-pairwise loop of the \texttt{DirectSum} struct in Rust}, label=code:rust-directsum-foreach-pairs]
fn for_each_particle_pairs_mut(&mut self, f: &(dyn Fn(&mut Particle, &Particle) + Send + Sync)) {
    let count = self.particle_count();

    for i in 0..count {
        // newtons third law: skip same pairs
        for j in (i + 1)..count {
            let (left, right) = self.particles.split_at_mut(j);
            f(&mut left[i], &right[0]);
            f(&mut right[0], &left[i]);
        }
    }
}
\end{lstlisting}

\begin{lstlisting}[style=eclipse-cpp, language=C++, basicstyle=\ttfamily\small, caption={The particle-pairwise loop of the \texttt{DirectSum} struct in C++}, label=code:cpp-directsum-foreach-pairs]
void for_each_particle_pairs_mut(std::function<void(Particle &, const Particle &)> callback) override
{
    for (size_t i = 0; i < particles_vec.size(); ++i)
    {
        for (size_t j = i + 1; j < particles_vec.size(); ++j)
        {
            auto& p1 = particles_vec[i];
            auto& p2 = particles_vec[j];
            callback(p1, p2);
            callback(p2, p1);
        }
    }
}
\end{lstlisting}

In C++, the naive approach is fairly trivial to implement. In Rust, we arrive at a problem caused by borrowing rules: Since borrowing one element of a vector borrows the entire vector (and borrowing one element of vector mutably borrows the entire vector mutably), we can not borrow two particles with one borrowed mutably, without breaking the safety rules.

This is because since the iterator uses a dynamic parameter -- the loop index -- the static analyzer is not able to verify whether the same particle value is borrowed mutably, which could cause a class of bugs Rust tries to prevent.

The solution is a method provided by Rusts' vector type, \texttt{split\_at\_mut}, which borrows the vector as two slices, split at a provided index. This allows us to borrow one particle mutably, and one immutably from the same structure.

\subsection{Linked Cells}

The second algorithmic approach is the \texttt{LinkedCells} implementation with cell management (chunks) to reduce computational workload.

You can see the definitions for the \texttt{LinkedCells} struct in Listings~\ref{code:rust-linked-cells-definition} (Rust) and~\ref{code:cpp-linked-cells-definition} (C++).

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption={The definition of the \texttt{LinkedCells} struct with the generic \texttt{Cell} in Rust}, label=code:rust-linked-cells-definition]
pub struct LinkedCells<Cell: ParticleContainer> {
    cells: HashMap<Vec3<i32>, Cell>,
    cell_size: Vec3<f64>,
}
\end{lstlisting}

\begin{lstlisting}[style=eclipse-cpp, language=C++, basicstyle=\ttfamily\small, caption={The definition of the \texttt{LinkedCells} struct with the generic \texttt{ParticleContainerT} in C++}, label=code:cpp-linked-cells-definition]
template <typename ParticleContainerT>
class LinkedCells : public ParticleContainer
{
    // assert that ParticleContainerT is a ParticleContainer
    static_assert(std::is_base_of<ParticleContainer, ParticleContainerT>::value, "ParticleContainerT must extend ParticleContainer");
    static_assert(std::is_default_constructible<ParticleContainerT>::value, "ParticleContainerT must be default-constructible");

    Vec3<double> cell_size;
    std::unordered_map<Vec3<int>, ParticleContainerT> particle_containers_chunk;
}
\end{lstlisting}

To ensure a fair comparison, we use a hashmap in Rust and an unordered map in C++ for the cells data structure, with the ``cell index'', the static cell position, used as the key. On paper this gives both data structure constant value access time.

As previously mentioned, the cell is an abstraction of another particle container, which per default is a smaller \texttt{DirectSum} container. The syntax difference for the ``for each particles'' method is highlighted in Listings~\ref{code:rust-linked-cells-foreach} (Rust) and~\ref{code:cpp-linked-cells-foreach} (C++).

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption={The definition of the \texttt{LinkedCells::for\_each\_particles} method in Rust. (Note: In the source code, we use more functional syntax with the \texttt{.value().for\_each(callback)} function, which was unrolled into a for loop.)}, label=code:rust-linked-cells-foreach]
fn for_each_particles(&self, callback: &(dyn Fn(&Particle) + Send + Sync)) {
    for cell in self.cells.values() {
        cell.for_each_particles(callback);
    }
}
\end{lstlisting}

\begin{lstlisting}[style=eclipse-cpp, language=C++, basicstyle=\ttfamily\small, caption={The definition of the \texttt{LinkedCells::for\_each\_particles} method in C++}, label=code:cpp-linked-cells-foreach]
template <typename ParticleContainerT>
void for_each_particles(std::function<void(const Particle &)> callback) const override
{
    for (const auto &pair : particle_containers_chunk)
    {
        pair.second.for_each_particles(callback);
    }
}
\end{lstlisting}

Both implementations follow a similar structure of taking the callback argument as a dynamic (virtual) object with the C++ \texttt{std::function} interface being equivalent to the \texttt{Fn} trait in Rust. The callback also implements the traits \texttt{Send} and \texttt{Sync}, which will be relevant in the parallelization section later. The iteration over cells is also trivial, as well as passing the callback recursively into the cells' \texttt{for\_each\_particles} invocation.

\subsection{Parallelization}

The third algorithmic approach is the \texttt{DirectSum} implementation with parallel execution on the pairwise loop, which accounts for the majority of the total runtime (whose exact percentage depends on the amount of particles, with higher particle counts reaching over $90\%$ of the runtime).

In C++ this is done with the OpenMP pragma invocation \texttt{omp parallel for} on the ``outer loop'' of the pairwise iteration. For Rust, we use Rayon, a parallelization library similar in usage to OpenMP (OMP). Both approaches can be seen in Listings~\ref{code:rust-parallel-foreach} (Rayon, Rust) and~\ref{code:cpp-parallel-foreach} (OpenMP, C++).

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption={The definition of the \texttt{LinkedCells::for\_each\_particle\_pairs\_mut} method in Rust.}, label=code:rust-parallel-foreach]
fn for_each_particle_pairs_mut(
    &mut self,
    f: &(dyn Fn(&mut Particle, &Particle) + Send + Sync),
) {
    let count = self.particle_count();
    let particles = PointerWrapper(self.particles.as_mut_ptr());

    // in c++ we parallelized outer loop too
    (0..count).into_par_iter().for_each(|i| unsafe {
        let mut left = &mut *particles.at(i);

        for j in 0..count {
            if i == j { continue; }
            let right = &*particles.at(j);
            f(&mut left, &right);
        }
    });
}
\end{lstlisting}

\begin{lstlisting}[style=eclipse-cpp, language=C++, basicstyle=\ttfamily\small, caption={The definition of the \texttt{LinkedCells::for\_each\_particle\_pairs\_mut} method in C++}, label=code:cpp-parallel-foreach]
void for_each_particle_pairs_mut(std::function<void(Particle &, const Particle &)> callback) override
{
#pragma omp parallel for
    for (size_t i = 0; i < particles_vec.size(); ++i)
    {
        auto& left = particles_vec[i];

        for (size_t j = 0; j < particles_vec.size(); ++j)
        {
            if (i == j) continue; // skip self-interaction
            const auto& right = particles_vec[j];
            callback(left, right);
        }
    }
}
\end{lstlisting}

Instead of pragmas (macros), Rayon uses Rust Traits to implement parallelization behaviour for iterators as seen with the \texttt{into\_par\_iter()} method above, which converts any iterable (data structure, range, etc.) into a parallel iterator.

There is not much to comment about the approach usage, however we had a problem in the Rust implementation due to the borrowing rules. The final approach uses unsafe code to allow parallel access on the particles struct, which will be described in the next paragraph.

\subsubsection{Unsafe Rust in the Parallel Approach}

In~\autoref{code:rust-parallel-foreach} we see the keyword \texttt{unsafe} used around the pairwise iteration. This is because Rust cannot statically analyze the safety of the scope which has mutable and non-mutable access of the particles data structure across threads.

What we do in the final implementation is converting the particles vector to a pointer of particles by borrowing it once. The problem with raw pointers however, is that passing them is not thread safe. What we do is create a wrapper struct \texttt{PointerWrapper} (see~\ref{code:rust-parallel-wrapper}) and assume it to be thread safe by implementing the unsafe traits \texttt{Send} and \texttt{Sync}.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption={The definition of the \texttt{PointerWrapper} struct in Rust.}, label=code:rust-parallel-wrapper]
pub struct PointerWrapper<T>(*mut T);
unsafe impl<T> Sync for PointerWrapper<T> {}
unsafe impl<T> Send for PointerWrapper<T> {}

impl<T> PointerWrapper<T> {
    unsafe fn at(&self, rhs: usize) -> *mut T {
        unsafe { self.0.add(rhs) }
    }
}
\end{lstlisting}

In terms of developer experience and usability, OpenMP in C++ scores better compared to Rust, as the workaround with thread safe pointers involves unsafe code and additional abstractions. Rust also loses on the compile-time statically analyzed safety with this approach.

\subsubsection{Fairness of the Comparison}

The comparison is fair since both libraries are highly popular within their language, but at the same time unfair due to the following technical reason:

OpenMP provides the developer with a low-level interface to map the program threads to the hardware directly, while Rayon is a high-level parallelism library which implements optimizations like work stealing~\cite{rust-rayon-work-stealing}, making Rayon capable of dynamically deciding how to balance the workload to make multithreading ``more profitable''. This is completely opposite to OpenMP's approach of giving the developer more tools and freedom.

There's been some studies in this particular field 7 years ago when Rayon was less mature than nowadays~\cite{rust-rayon-carnegie-mellon-university} showcasing multiple different insights, in part even contradicting to the results presented by this thesis.

% One insight was that for matrix multiplication, OpenMP performed best at 8 threads and had a performance decline afterwards, while Rayon performed better for higher thread counts. We will observe similar artefacts later in this thesis.

To ensure that performance does not decline severely    between two commits, and that the simulation remains numerically correct and equal across changes, we implemented a Continuous Integration (CI) pipeline using GitHub Actions, which runs on push.

In the past, this workflow helped narrow down performance-critical errors, such as building in debug mode, allocating unused variables on the heap or even passing one-element vectors as a function argument, when just passing the item was also viable. We always attempted to improve the worse-performing language, and in some early benchmarks C++ outperformed Rust. By now both languages approached their performance limits in the scope of optimal, naive implementations.

In the parallelized DirectSum implementation for both Rust and C++, we only parallelize the code segment which performs operations for every particle pair by parallelizing the `outer' iteration and keeping the `inner' iteration sequential. We should also note here that we do not really compare the capacities of the programming languages here, but of two specific parallelization libraries.

For Rust, we use Rayon as the parallelization library, and for C++ we use OMP. The thread count was set with environment variables \texttt{RAYON\_NUM\_THREADS} and \texttt{OMP\_NUM\_THREADS}.

The first artefact we observe in the benchmarks (see~\ref{fig:benchmark-parallel}) is that there are specific thread counts where OMP performance drops. On the machine where the benchmarks were run, there was a 1066ms drop between thread counts 8 and 9, and a 1508ms drop between thread counts 20 and 21. A similar artefact has also been observed by other studies~\cite{rust-rayon-carnegie-mellon-university}.

The artefacts can generally be explained with OMP giving the developer more low-level control over thread-to-hardware assignments, and Rayon taking a more high-level approach. The performance decline at 21 threads can be explained with operating system overhead: When there are more threads requested than resources available, the scheduling overhead of dispatching threads starts to affect measurements.

To understand the artefact at 8 to 9 threads, we will measure OMP performance with different thread-to-hardware mappings in the next figure.

In~\autoref{fig:benchmark-parallel-omp-modi} we see OMP tested with different modi in a more controlled environment to understand the artifacts seen previously in~\autoref{fig:benchmark-parallel}. `Close' and `Spread' defines the value of the environment variable \texttt{OMP\_PROC\_BIND}, and `Cores' and `Threads' defines the value of the environment variable \texttt{OMP\_PLACES}.

Intuitively, `Close' means we claim resources in close proximity, and `Spread' means we use distant resources, with `Cores' and `Threads' selecting what to count as a resource. For example, `Close Threads' means we use nearby threads, even if they share the same core and cache, while `Close Cores' will try to use different nearby cores, even if it skips some threads.

We define the two ``curves'' seen in ~\autoref{fig:benchmark-parallel-omp-modi} as follows: The ``efficient'' curve follows ``Close Threads'' from threads 2 to 20. The ``performant'' curve follows ``Close Cores'' from threads 1 to 8.

Recall that according to the product specification of the CPU used for benchmarking\cite{cpu-intel-core-i7-12700k}, we have 8 dual-threaded performance cores which run at a base frequency of 3.60 GHz, and 4 efficiency cores running at 2.70 GHz. With this information in mind we will give an individual explanation for the artefacts seen above.

\begin{description}
    \item[Close Threads] We do not see a performance decline for this configuration, however at threads 1 to 2 we can see a visual jump to the efficient curve as we start using two threads within the same core using Intel(R) Hyper-Threading Technology.

    Since the two threads share the same L1 and L2 caches, frequent cache rewrites from different threads occur, reducing the overall performance speedup due to cache misses.

    \item[Spread Cores] The performance decline occurs at 2 to 3 threads. Since we are unlikely to use threads in close proximity, the most likely explanation is that we use efficiency cores, which run at a lower base frequency and lead to overall slower performance.

    \item[Spread Threads] The performance decline occurs at 4 to 5 threads respectively. The explanation is analogous to Spread Cores.

    \item[Close Cores] The performance decline occurs at 8 to 9 threads, as we run out of performance cores, we either have to use an efficiency core or share the cores cache, both leading to undesired performance loss.
\end{description}

\chapter{Discussion and Conclusion}

The results presented in this thesis show that Rust is at least as competitive with C++ in terms of performance, but also outperforms C++ in memory safety models, overall developer experience, ecosystem and tooling.

However, it is important to highlight that the results are subject to implementation bias with non-zero cost abstractions used in the hot loop of the physics implementation. In this work, we compare Rusts' \texttt{HashMap} against C++ \texttt{unordered\_map}, we use dynamic dispatch and minor differences in memory layout and compiler optimizations can contribute to the observed performance differences. Since the hot loop is subject to these paradigms, a small relative performance difference is instantly upscaled in the benchmarks.

The Rust compiler \texttt{rustc} uses LLVM and the C++ code was compiled with the CMake default (which is GCC), which make different trade-offs in inling, loop-unrolling and link-time optimizations.

The parallelization implementations are also not comparable due to different threading models, with Rayon being more high-level and memory safe, and OMP giving more hardware control at the cost of relying on unsafe memory models.

The conclusion of the thesis suggests that Rust offers the following.

\begin{description}
    \item[Competitive Performance] The sequential benchmarks show that Rust is in general a bit faster, with some exceptional implementations outperforming C++ by up to $25\%$. The parallel performance seems to be processor-dependent.

    \item[Memory Safety] The type system and ownership model of Rust is a significant advantage, with guarantees on memory safety reducing the cognitive overhead in comparison to C++, where the developer is themselves responsible for memory allocation and freeing.

    \item[Ecosystem and Tooling] Rust provides a good set of tools with its package manager and community-written dependencies, which enhance productivity and developer experience. The integrated compiler, documentation generator, linter and error messages provide a good guidance for creating new software and maintaining it.
\end{description}

However, this does not mean that everyone should write all new or rewrite existing applications in Rust, because of the following reasons:

\begin{description}
    \item[Technical Debt] The attempt to rewrite large C++ codebases introduces technical debt. Incremental adoption with interoperability, as practiced by Google, is a more realistic approach to code migration.
    \item[Learning Curve] Rust has a higher learning curve than C++ because it does not use Java-style OOP concepts like abstract classes and inheritance. Instead, it relies on traits and patterns from functional programming. This requires to relearn most concepts from scratch in Rust.
    \item[Dependencies] Rust's ecosystem, despite growing rapidly, is still lacking some field-specific libraries, requiring additional effort to either bind C++ code or rewrite entire components in Rust. One such example is the LLVM project, which the Rust compiler relies on, but is written in C++.
    \item[Well-optimized Projects] For projects that are already well optimized and understood in C++, the rewrite in Rust may not yield much better performance.
\end{description}

In conclusion, Rust is a good alternative to C++ for new projects that involve security and maintainability, as Rust offers better tooling to start applications and immediately start coding, reduces configuration overhead, offers strong performance and introduces memory safety without garbage collection.

However, the decision to adopt Rust (or any other programming language) for a project should be assessed based on project requirements, team expertise and existing infrastructure.

This thesis contributes data and insights to inform that decision, demonstrating that Rust is a safe and performant language.

\section{Rust Traits with Ambiguity}\label{section:rust-trait-same-identifier}

This section aims to provide some understanding on how Rust determines which function is executed when a type implements multiple traits that share a common method identifier.

Generally, trait methods are not seen in a scope even if the struct implements them. In Rust, you have to explicitly include the trait in the scope where you wish to use it. Consider the following code to be in \texttt{foobar.rs}:

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small]
pub struct FooBar;

pub trait Foo {
    fn foobar(&self) {
        println!("Foo");
    }
}

pub trait Bar {
    fn foobar(&self) {
        println!("Bar");
    }
}

impl Foo for FooBar {};
impl Bar for FooBar {};
\end{lstlisting}

In this definition we have a struct \texttt{FooBar}, which implements the traits \texttt{Foo} and \texttt{Bar}. Since both traits define a method with the same name, this can cause ambiguity in code execution. Consider the following three examples in \texttt{main.rs}, and an explanation below if it will or why not compile.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small]
mod foobar; // this declares foobar.rs 
use foobar::FooBar; // this imports the FooBar struct

fn main() {
    let x = FooBar;
    x.foobar();
}
\end{lstlisting}

The example above will not compile. Per default, trait methods are tied with the trait they belong to in Rust, which is required to be imported in the scope.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small]
mod foobar; 
use foobar::{FooBar, Foo}; // also import Foo

fn main() {
    let x = FooBar;
    x.foobar(); // prints `Foo'
}
\end{lstlisting}

The example above will compile as the \texttt{Foo} trait is imported and therefore visible on structs that implement it.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small]
mod foobar; 
use foobar::{FooBar, Foo, Bar}; // imports both traits

fn main() {
    let x = FooBar;
    x.foobar();
}
\end{lstlisting}

The example above will not compile, as \texttt{foobar()} is ambiguous. The solution is to rewrite the last line into \texttt{Foo::fobar(x)} if we want to print `Foo'. By using the path notation, the ambiguity is resolved. Intuitively, this makes the method static with a clear, unique name.

\section{Overloading Operators}\label{section:rust-implement-add-appendix}

Implementing the traits like \texttt{Add} or \texttt{Mul}, which are linked with the infix operators $+$ and $*$, requires a combination of concepts which would be confusing in the main body of the thesis. This section will explain the concepts which give Rust traits more powers in more detail. First take a look at~\autoref{code:rust-trait-implement-add}.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption={A Trait definition in Rust (Do not be confused that there is no \texttt{return} keyword: The last line is considered the return value if it is not followed by a semicolon)}, label=code:rust-trait-implement-add]
impl<T: Mul<Output = T> + Copy> Mul<T> for Vec3<T> {
    type Output = Self;

    fn mul(self, scalar: T) -> Self::Output {
        Self {
            x: self.x * scalar,
            y: self.y * scalar,
            z: self.z * scalar,
        }
    }
}
\end{lstlisting}

Unlike the more simple trait definition in~\autoref{code:rust-trait}, the \texttt{Mul} trait has generics, type bounds and trait types.

Generics are near identical to the C++ \texttt{template} concept: Defined in angle brackets, a generic is a type paramater appended after the trait name, for example in \texttt{Mul<Rhs>} \texttt{Rhs} is the generic parameter of the \texttt{Mul} trait. This allows for simple templating of a trait and implementing it for different types. For example, a string buffer can implement \texttt{Add<\&str>} and \texttt{Add<char>} to support both concatenation with string literals and characters. Note, that when implementing a trait with generics for a type, you need to specify the generic after the \texttt{impl} keyword to indicate it's a local generic and not a foreign type.

Type bounds can be added with a semicolon, or a special \texttt{where}-clause and are used to specify a set of traits which the generic implements -- in other words, it implements the trait conditionally for generic parameters which implement the type bounds. In~\autoref{code:rust-trait-implement-add}, we implement the multiplication behaviour for a vector struct containing the attributes \texttt{x}, \texttt{y} and \texttt{z} of type \texttt{T}.

We bind the generic parameter \texttt{T} to implement the traits \texttt{Mul<Output = T>} and \texttt{Copy}. In the trait scope, we can then use the bound behaviour of \texttt{T} without knowing the underlying type, as seen in the expression \texttt{self.x * scalar}.

\section{More Depth to Ownership}\label{section:rust-ownership-appendix}

Since ownership and references are best understood intuitively instead of theoretically, this sections aims to provide some more Rust examples to get familiarity with the core of Rusts' type system.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, label=code:rust-ownership-appendix-example1]
fn main() {
    let mut text = String::from("Hello");    // String
    let names = ["Teto", "Yuki", "Flower"];  // slice of &str

    for name in names {
        text += ", ";
        text += name;
    }

    println!("{}", text);
}
\end{lstlisting}

In the example above, we iterate over all names in an array to greet them.

We have an owned value \texttt{text}, which manages text content on the heap. This string can be cleared, extended and modified in any other way. We add the \texttt{mut} modifier to use the mutable features of the string manager.

The variable \texttt{names} is also an owned value of the type \texttt{[\&str; 3]} -- an array of length 3 of string slices. Since these strings are located in the data segment of the resulting binary, the contents of the array are immutable string slices \texttt{\&str}. You can think of it this way: The C++ equivalent of \texttt{String} is \texttt{std::string} and the equivalent of \texttt{\&str} is \texttt{const char*}.

% In the for loop, we iterate over all entries of the \texttt{names} slice. The method itself borrows \texttt{names} immutably to create an iterator over all elements. Then, we append the name to the mutable string variable \texttt{text}. Afterwards, the resulting string contents are printed to the console.

Since the syntactic sugar in~\autoref{code:rust-ownership-appendix-example1} of the add-assign operator (\texttt{+=}) hides how the references are passed to the string concatenation behaviour, the following code example will unpack the syntactic sugar to provide a better explanation. You should keep in mind that the syntactic sugar \texttt{a += b} is converted to the trait method \texttt{a.add\_assign(b)}. Additionally, as mentioned in appendix note~\ref{section:rust-trait-same-identifier}, any method \texttt{value.func(arg1)} can also be further converted using the path notation into a static function \texttt{Ty::func(value, arg1)} with the appropriate borrow modifiers.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, label=code:rust-ownership-appendix-example2]
fn main() {
    use std::ops::AddAssign;

    let mut text = String::from("Hello");
    let names = ["Teto", "Yuki", "Flower"];

    for name in names.iter() {
        // first add_assign borrows 'text' mutably
        AddAssign::<&str>::add_assign(&mut text, &", ");
        // add_assign releases borrow
        // second add_assign borrows 'text' mutably
        AddAssign::<&str>::add_assign(&mut text, &name);
        // add_assign releases borrow
    }   // for next loop iteration, 'text' can be borrowed

    println!("{}", text);
}
\end{lstlisting}

In the for loop, we edit the variable \texttt{text} two times. This is perfectly fine, since the logic occurs sequentially and every time we modify \texttt{text}, the borrow is released. After every loop iteration the variable is free of further borrow claims (R4). Every variable is also valid (R5), which means the reference rules are followed in this example.

The ownership rules are also followed, with the variables \texttt{text} and \texttt{names} being dropped at the end of the function scope (R3). The first rule ``The value has an owner'' is followed also for static string constants, since the data segment is their owner.

The static analyzer will treat for loops as repeating scopes, which means the compiler ensures the rules are followed across iterations. This makes the following code illegal:

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small]
fn main() {
    let mut text = String::from("Hello");
    let names = ["Teto", "Yuki", "Flower"];

    for name in names.iter() {
        let a = text; // iteration 1: 'a' moved
                      // iteration 2: cannot move (already moved)
    }
}
\end{lstlisting}

In the thesis code, this behaviour caused design problems when writing the particle pairs iteration. The example below highlights the problem. We are given a nested for loop, with the outer loop borrowing the particles vector mutably, and the inner loop immutably.

The callback type is an anonymous function taking two particles, with the first borrowed mutably, and the second immutably. The idea is to add the force interaction to the first argument only.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption={First approach at DirectSum particle pairs iteration.}]
type Callback = dyn Fn(&mut Particle, &Particle) + Send + Sync;

impl ParticleContainer for DirectSum {
    fn for_each_pairs_mut(&mut self, callback: &Callback) {
        let count = self.particle_count();

        for p1 in self.particles.iter_mut() {
            for p2 in self.particles.iter() {
                if p1 == p2 { continue; }

                callback(&mut p1, &p2);
            }
        }
    }
}
\end{lstlisting}

The problem with this code is, that it breaks the Fourth Rule: Line 7 borrows the \texttt{self.particles} value mutably, and during this borrow line 8 also borrows the value immutably. This is not allowed.

The second approach that was attempted was to iterate over the indices of the particles, and manually retrieve them, as seen below. The \texttt{..} symbol is syntactic sugar for an integer range.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption={Second approach at DirectSum particle pairs iteration.}]
type Callback = dyn Fn(&mut Particle, &Particle) + Send + Sync;

impl ParticleContainer for DirectSum {
    fn for_each_pairs_mut(&mut self, callback: &Callback) {
        let count = self.particle_count();

        for i in 0 .. count {
            for j in 0 .. count {
                if i == j { continue; }

                let p1 = self.particles.get_mut(i);
                let p2 = self.particles.get(i);

                callback(&mut p1, &p2);
            }
        }
    }
}
\end{lstlisting}

The problem remains: Since \texttt{get(index)} and \texttt{get\_mut(index)} borrow the entire particles vector, we run into a problem where the naive approach does not work in Rust. The solution is to use the vector method \texttt{split\_at\_mut(index)}.

This function logically splits the vector into two slices, the left-hand side and the right-hand side. This way, it is possible to modify multiple items in a vector. The resulting code is given below.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption={Second approach at DirectSum particle pairs iteration.}]
type Callback = dyn Fn(&mut Particle, &Particle) + Send + Sync;

impl ParticleContainer for DirectSum {
    fn for_each_pairs_mut(&mut self, callback: &Callback) {
        let count = self.particle_count();

        for i in 0 .. count {
            for j in 0 .. count {
                if i == j { continue; }

                let (left, right) = self.particles.split_at_mut(j);

                let p1 = left.get_mut(i);
                let p2 = right.get(0);

                callback(&mut p1, &p2);
            }
        }
    }
}
\end{lstlisting}

The main insight here is, that this simple behaviour would be trivial to implement in C++, but due to Rust ownership rules which enforce memory safety, the pair iterator approach is a bit tricky to implement.

In~\autoref{fig:benchmark-strong-scaling} we can see the C++ implementation with Close Cores configuration benchmarked against Rust in a logarithmic strong scaling diagram. The dotted line shows the theoretically achievable speedup under the assumption that $k$ threads will speed up the program by a factor of $k$.

For computer algorithms this is almost never possible because the parallelization overhead and the sequential part of the program will outweigh the benefits of further threads as the execution time of the parallel code part approaches zero.

At 40 threads we can also observe the performance drop for the C++ implementation. This is by design of the supercluster CoolMUC4: It has 2 sockets, each with 40 cores. When we use more than 40 cores, the program no longer profits from cache locality as some communication is done through the slower inter-socket bus system. Despite the performance drop, OpenMP (C++) still shows a higher speedup compared to Rayon (Rust), reaching at least a speedup of 16, while Rust stagnates at a speedup of 11.
