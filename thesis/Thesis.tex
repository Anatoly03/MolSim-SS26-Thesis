\vspace*{2cm}
\begin{center}
    {\Large \bf Abstract}
\end{center}
\vspace{1cm}

In the past decades, Rust has gained more admiration as a low-level, performant, memory-safe programming language, while C++ remains the dominant choice for high-performance computing in the academic field. This thesis presents empirical results by writing six molecular dynamics implementations for both Rust and C++.

Both languages implement three different approaches of particle management and computation patterns, with DirectSum computing over all particle pairs in the hot loop, LinkedCells introducing a three-dimensional chunk system to reduce the overall workload, and DirectSumParallel using multi-threaded paradigms to accelerate computation.

This thesis aims to inform the decision of adopting Rust in emerging software for performance-critical applications with high memory-safety requirements.

\section{The Rust Ecosystem}

Before diving into the the syntax and the defining elements of the Rust Programming Language, this section will give a brief overview over the tooling and console applications provided by Cargo, the Rust Package Manager.

Since Cargo can install dependencies it was also designed to be extensible, meaning that most operations you will need to maintain a Rust project are located behind a Cargo subcommand.

\begin{description}
    \item[cargo run] Equivalent to \texttt{make run}, Cargo will invoke the Rust compiler on the codebase and execute the resulting binary.
    \item[cargo build] Equivalent to \texttt{make}, Cargo will invoke the Rust compiler on the codebase and compile a binary but not execute it.
    \item[cargo test] Equivalent to \texttt{ctest} or GoogleTest, Cargo has an integrated testing tool which will compile the codebase and run all functions annotated with \texttt{\#[test]} as an individual, isolated test case.
    \item[cargo doc] Equivalent to \texttt{Doxygen} or other documentation libraries, Cargo provides an in-built way of generating documentation for the codebase.
    \item[cargo fmt] Equivalent to \texttt{clang-format}, Cargo provides an in-built way to format the entire codebase.
    \item[cargo clippy] Equivalent to \texttt{clang-tidy}, Cargo provides an in-built way to lint and statically analyze the codebase. This command is also often used in CI/CD to ensure the codebase quality.
\end{description}

\subsection{Structs and Traits}

Structs in Rust are almost entirely equivalent to C++ structs. A struct is a type which defines a collection of fields. Unlike in C++ however, Rust has no concept of struct inheritance. Instead of abstract classes, Rust provides traits\cite{rust-book-traits}, an abstract interface that types can implement explicitly. This introduces the concept of composability in Rust, giving one type the feature to express multiple traits.

pub trait Force {
    fn potential(&self, particle: &Particle, other: &Particle)
        -> f64;

    fn force(&self, particle: &Particle, other: &Particle) -> Vec3 {
        let potential = self.potential(particle, other);
        let diff = Particle::position_difference(other, particle);
        -diff * (potential / diff.length2())
    }
}
\end{lstlisting}

A trait is, more comparable to the concept in Java, an abstract interface, defining the interface name and a collection of methods. Some methods can have a default definition and thus do not need to be redefined. Traits are explicitly implemented for types with an implementation block.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption=An implementation of the Force trait in Rust (Note: A comparison wether distance is zero is omitted for code flow simplicity), label=code:rust-trait-implement]
impl Force for NewtonForce {
    fn potential(&self, particle: &Particle, other: &Particle)
    -> f64 {
        let distance = Particle::distance(particle, other);
        let mass_prod = Particle::mass_product(particle, other);
        -self.factor * mass_prod / distance
    }
}
\end{lstlisting}

Similar to C++ operator overloads, Rust backes some operators by traits, providing similar syntactic sugar to overload certain operators.

For example the infix notation of the $+$ operator can be defined with the trait \texttt{Add<Rhs>}, where the self type acts as left hand side and a generic type defines the type of the right hand side. This way string buffers can be concated over the same operator as integers are being summed over. In listing~\ref{code:rust-trait} we overload the $*$ operator to allow multiplication of the custom vector type implementation with a scalar.

This `atomicity' of an implementation block is good for two reasons: Firstly, it allows for code readability, differentiating between ``type methods'' and ``trait implementation''. Secondly, this prevents a collision between traits using the same identifier for a method.

\subsection{Dynamic Dispatch}

Both the C++ and Rust implementations use dynamic dispatch to convert a type into an interface at runtime. This is not a zero-cost abstraction, but allows for a fair comparison and code writing simplicity.

For example, the types \texttt{NewtonForce} and \texttt{LennardJonesForce} both implement (or inherit for the C++ codebase) the \texttt{Force} trait. At the cost of losing all information on the underlying type, we get a black box of a model, capable of yielding the potential and force interaction for any two particles.

\subsection{Unsafe Rust}

What we have learned so far has been `Safe Rust', which can be statically analyzed for memory safety and bugs that would cause segmentation fault in C++ are caught in the compilation stage.

However sometimes because of performance reasons or communicating with an external library, code has to be written using of raw pointer arithmetics. This mode is commonly referred to as `Unsafe Rust'.

An unsafe functionality is a scope, function or trait implementation annotated with the \texttt{unsafe} keyword. In an unsafe block, Rust gives you access to a few operations which can not be statically verified and could cause undefined behaviour. The operations are the following.

\begin{enumerate}
    \item Dereferencing a pointer.
    \item Using other unsafe functionalities like invoking an unsafe function or implementing an unsafe trait.
    \item Read or write to a mutable static variable.
    \item Accessing fields of a \texttt{union}, a special element which is syntactically similar to a struct with the exception of all fields sharing the same storage.
\end{enumerate}

To get a bit of intuition on what kind of operations are unsafe consier this example: For a struct to be shared accross threads, it needs to implement the \texttt{Sync} trait, which is unsafe. If the struct also contains a pointer which you would like to interpret at index $2$, adding $2$ to the pointer and dereferencing it is also unsafe behaviour.

\subsection{Clap}

Clap is used in the program frame, it provides a macro capable of parsing a struct and generating the command line parser, mapping console input to values in the struct. This helps keep the code quality much cleaner and removes the need of \texttt{getopt}'s seemingly magic syntax. The command line parser is generate with \texttt{\#[derive(Parser)]}

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small, caption=An example of using clap in Rust, label=code:rust-clap]
/// The comment will be visible with --help
#[derive(Parser)]
struct Args {
    /// Positional argument.
    input: PathBuf,

    /// Non-positional argument.
    #[arg(short, long, default_value = "output/out.vtk")]
    output: PathBuf,

    /// Simulation time step.
    #[arg(short, long)]
    delta_time: Option<f64>,
}
\end{lstlisting}

The above figure shows a struct definition annotated with macros and attributes from the Clap crate. The line \texttt{let args = Args::parse()} can then be used in the main function to invoke the command line parser and retrieve all arguments. This moves the input validation completely to a depenency and is a huge improvement in comparison to \texttt{getopt}.

To make for a fair comparison to C++, it is crucial to add that there are CLI parser alternatives in the C++ ecosystem which are more modern, feature-rich and provide better error handling like CLI11\cite{cpp-cli11}.

\subsection{Serde}

Serde is the standard of serialization and deserialization across the Rust package ecosystem, having reached over 1 billion all-time downloads\cite{rust-crates-serde}. It provides the traits \texttt{Serialize} and \texttt{Deserialize} that map Rust types into and from an internal data format. Various data formats like JSON, YAML or VTU can then implement the traits \texttt{Serializer} and \texttt{Deserializer} to communicate with Serde's internal data format.

The derive macros \texttt{\#[derive(Serialize, Deserialize)]} can be used to automatically generate the proper mapping. In the project this is extremely helpful for the structs \texttt{FileDefinition} and \texttt{Particle}. This way most of the input validation is once again moved to a dependency and there is no need implement checks for missing fields yourself.

Rayon is a parallelization library similar to OMP. Instead of pragmas, Rayon uses Rust Traits to implement parallelization behaviour for iterators.

\chapter{Application with Molecular Dynamics}

In this chapter we will explain the molecular dynamics algorithms from a mathematical and theoretical perspective and the next chapter will dive into a more detailed technical explanation about the implementation.

We define force as the equation $F_X = -\frac{U_X}{r}$, with $r$ being the scalar distance between two particles and we call $U_X$ the potential. We mostly work with Lennard-Jones interactions $F_\text{LJ}$ in this thesis, however as an artefact from a legacy project we also support the Newtonian force calculation $F_\text{N}$. In other words, the algorithm sees the force $F$ as an abstract interface. The formulas for the Newton potential $U_\text{N}$ and the Lennard Jones Potential $U_\text{LJ}$ are given as follows.

\begin{align}
U_\text{N} := - G \cdot \frac{M}{r}
\end{align}\label{potential-newton}

\begin{align}
U_\text{LJ} := 4 \cdot \epsilon \cdot \left[{{\left(\frac{\sigma}{r}\right)}^{12}} - {{\left(\frac{\sigma}{r}\right)}^6}\right]
\end{align}\label{potential-lennard-jones}

For the Newton potential, $G = 1$ is the gravitational constant and $M$ the product of the particle masses. For the Lennard Jones potential it is enough to say that $\epsilon = 5$ and $\sigma = 1$ are arbitrary constants. We will not get to an intuitive understanding of what these constants represent.

In the parallelized DirectSum implementation for both Rust and C++ we only parallelize the code segment which performs operations for every particle pair, by parallelizing the `outer' iteration and keeping the `inner' iteration sequential. We should also note here, that we don't really compare the capacities of the programming languages here, but of two specific parallelization libraries.

For Rust, we use Rayon as the parallelization library, and for C++ we use OMP. The thread count was set with environment variables \texttt{RAYON\_NUM\_THREADS} and \texttt{OMP\_NUM\_THREADS}.

The first artefact we observe is that there are specific thread counts, where OMP performance drops. On the machine where the benchmarks were run, there was a 1066ms drop between thread counts 8 and 9, and a 1508ms drop between thread counts 20 and 21.

The artefacts can generally be explained with OMP giving the developer more low-level control over thread to hardware assignments, and Rayon taking a more high-level approach. The performance decline at 21 threads can be explained with operating system overhead: When there are more threads requested than resources available, the scheduling overhead of dispatching threads starts to affect measurements.

To understand the artefact at 8 to 9 threads, we will measure OMP performance with different thread-to-hardware mappings in the next figure.

% The performance spikes can be explained by the choice of CPU and the fact that OMP provides the developer with full control over thread distribution:

% For the first scenario, a new thread will compute at a lower base frequency, making the other 8 threads finish faster and having to wait the remaining time. In the second scenario, we compute at another thread in the same core, leading to more frequent cache rewrites, and therefore cache misses, which also leads to a performance drop. The performance drop is marked with vertical dashed lines in figure~\ref{fig:benchmark-parallel}.

% This is probably because OMP takes the environment variable without further preprocessing and Rayon prefers the smaller of the environment variable and logical cores.

% At above 20 threads, OMP reaches the CPU limits and the operating systems' overhead affects the measurements negatively.

% It's also noteworthy that above 20 threads, the the C++ implementation shows no stable performance pattern, this is most likely because at an overhead this high, the operating software dispatcher affects measurements.

% At 2 threads, Rust parallel DirectSum completes in $88.5\%$ of the time taken by the C++ parallel DirectSum implementation, with a speedup of $22.6\%$. In~\autoref{fig:benchmark-parallel-omp-modi} we see OMP tested with different modi in a more controlled environment to understand the artifacts seen previously in~\autoref{fig:benchmark-parallel}. `Close' and `Spread' defines the value of the environment variable \texttt{OMP\_PROC\_BIND} and `Cores' and `Threads' defines the value of the environment variable \texttt{OMP\_PLACES}.

Intuitively, `Close' means we claim resources in close proximity, and `Spread' means we use distant resources, with `Cores' and `Threads' selecting what to count as a resource. For example `Close Threads' means we use nearby threads, even if the share the same core and cache, while `Close Cores' will try to use different nearby cores, even if it skips some threads.

We define the two ``curves'' seen in ~\autoref{fig:benchmark-parallel-omp-modi} as following: The ``efficient'' curve follows ``Close Threads'' from threads 2 to 20. The ``performant'' curve follows ``Close Cores'' from threads 1 to 8.

According to the product specification of the CPU used for benchmarking\cite{cpu-intel-core-i7-12700k}, we have 8 performance cores running at a base frequency of 3.60 GHz, each having two threads using Intel(R) Hyper-Threading Technology, and several further efficiency cores running at 2.70 GHz. With this information in mind we will give an individual explanation for the artefacts seen above.

\begin{description}
    \item[Close Threads] We don't really see a performance decline for this configuration, however at threads 1 to 2 we can see a visual jump to the efficient curve as we start using two threads within the same core. One explanation here could be NUMA effects, which lead to rewrites in the cores' cache.

    \item[Spread Cores] The performance decline occurs at 2 to 3 threads. Since we are unlikely to use threads in close proximity, the most likely explanation is that we use efficiency cores, which run at a lower base frequency and lead to overall slower performance.

    \item[Spread Threads] The performance decline occurs at 4 to 5 threads respectively. The explanation is analogous to Spread Cores.
    
    \item[Close Cores] The performance decline occurs at 8 to 9 threads, as we run out of performance cores, we either have to use an efficiency core or share the cores cache, both leading to undesired performance loss.
\end{description}

\chapter{Discussion and Conclusion}

The results presented in this thesis show that Rust is at least as competitive with C++ in terms of performance but also outperforms C++ in memory safet models, overall developer experience, ecosystem and tooling.

However it is important to highlight that the results are subject to implementation bias with non-zero cost abstractions used in the hot loop of the physics implementation. In this work, we compare Rusts' \texttt{HashMap} against C++ \texttt{unordered\_map}, we use dynamic dispatch and minor difference in memory layout and compiler optimizations can contribute to observed performance differences. Since the hot loop is subject to these paradigms, a small relative performance difference is instantly upscaled in the benchmarks.

The Rust compiler \texttt{rustc} uses LLVM and the C++ code was compiled with the CMake default (which is GCC), which make different trade-offs in inling, loop-unrolling and link-time optimizations.

The parallelization implementations are also not directly comparable due to different threading models, with Rayon being more high-level and memory safe and OMP giving more hardware control at the cost of relying on unsafe memory models.

The conclusion of the thesis suggests that Rust offers the following.

\begin{description}
    \item[Competitive Performance] The sequential benchmarks show that Rust is in general a bit faster with some exceptional implementations outperforming C++ up to $25\%$ faster.

    \item[Memory Safety] The type system and ownership model of Rust is a significant advantage, with guarantees on memory safety reducing the cognitive overhead in comparison to C++, where 

    \item[Ecosystem and Tooling] Rust provides a good set of tools with its' package manager and community-written dependencies, which enhance productivity and developer experience. The integrated compiler, documentation generator, linter and error messages reduce the  
\end{description}

However, this does not mean that everyone should write all new or rewrite existing applications in Rust, because of the following reasons.

\begin{description}
    \item[Technical Debt] The attempt to rewrite large C++ codebases introduces technical debt. Incremental adoption with interoperability, as practiced by Google, is a more realistic approach to code migration.
    \item[Learning Curve] Rust has a higher learning curve than C++ because it does not use Java-style OOP concepts like abstract classes and inheritance. Instead it relies on traits and patterns from functional programming. This requires to relearn most concepts from scratch in Rust.
    \item[Dependencies] Rusts' ecosystem, despite growing rapidly is still lacking some field-specific libraries, requiring additional effort to either bind C++ code or rewrite entire components in Rust. One such example is the LLVM project, which the Rust compiler relies on, but is written in C++.
    \item[Well-optimized Projects] For projects that are already well optimized and understood in C++, the rewrite in Rust may not yield much better performance.
\end{description}

In conclusion, Rust is good alternative to C++ for new projects that involve security and maintainability, as Rust offers better tooling to start applications and immediately start coding, reduces configuration overhead, offers strong performance and introduces memory safety without garbage collection.

However the decision to adopt Rust (or any other programming language) for a project should be assesed based on project requirements, team expertise and existing infrastructure.

This thesis contributes data and insights to inform that decision, demonstrating that Rust is a safe and performant language.

\section{Rust Traits with Ambiguity}\label{section:rust-trait-same-identifier}

This section aims to provide some understanding on how Rust determines which function is executed when a type implements multiple traits that share a common method identifier.

Generally, trait methods are not seen in a scope even if the struct implements them. In Rust, you have to explicitly include the trait in the scope where you wish to use it. Consider the following code to be in \texttt{foobar.rs}

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small]
pub struct FooBar;

pub trait Foo {
    fn foobar(&self) {
        println!("Foo");
    }
}

pub trait Bar {
    fn foobar(&self) {
        println!("Bar");
    }
}

impl Foo for FooBar {};
impl Bar for FooBar {};
\end{lstlisting}

In this definition we have a struct \texttt{FooBar}, which implements the traits \texttt{Foo} and \texttt{Bar}. Since both traits define a method with the same name, this can cause ambiguity in code execution. Consider the following three examples in \texttt{main.rs}, and an explanation below if it will or why not compile.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small]
mod foobar; // this declares foobar.rs 
use foobar::FooBar; // this imports the FooBar struct

fn main() {
    let x = FooBar;
    x.foobar();
}
\end{lstlisting}

The example above will not compile. Per default, trait methods are tied with the trait they belong to in Rust, which is required to be imported in the scope.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small]
mod foobar; 
use foobar::{FooBar, Foo}; // also import Foo

fn main() {
    let x = FooBar;
    x.foobar(); // prints `Foo'
}
\end{lstlisting}

The example above will compile as the \texttt{Foo} trait is imported and therefore visible on structs that implement it.

\vspace{0.5em}
\begin{lstlisting}[style=eclipse-rust, language=Rust, basicstyle=\ttfamily\small]
mod foobar; 
use foobar::{FooBar, Foo, Bar}; // imports both traits

fn main() {
    let x = FooBar;
    x.foobar();
}
\end{lstlisting}

The example above will not compile, as \texttt{foobar()} is ambiguous. The solution is to rewrite the last line into \texttt{Foo::fobar(x)} if we want to print `Foo'. By using the path notation, the ambiguity is resolved. Intuitively, this makes the method static with a clear, unique name.

On CoolMUC4, sequential code performs slower than on a high-end consumer CPU, as the supercomputer operates on a lower frequency. The strength of CoolMUC comes from the evenly distributed workload, generally preventing artefacts as seen in~\autoref{fig:benchmark-parallel}.

However as it turns out, The Close Threads configuration performs poorly even on CoolMUC. This is because the CPU used on the supercomputer also makes use of Intel(R) Hyper-Threading Technology, with a pair of cache-sharing threads per core.
